# Adaptive workflow

Use the stages as a decision aid, not a mandatory checklist. Move to the stage that resolves the current uncertainty; loop back when new evidence changes the framing.

## Explore

First determine whether the active request is to design a product/Skill (design intent), perform a task directly (execution intent), or genuinely ambiguous. Use the whole conversation: “I want a Skill that helps me learn GitHub” is a product-design request, while “Explain GitHub Gist” is a direct explanation request. Keep the current design task active unless the user explicitly switches it. Read what the user has already supplied. Identify the intended user, situation, pain or opportunity, desired outcome, constraints, and decision they need. Do not ask for facts already present. If motivation is unclear, ask one open question such as “What made this worth solving now?” If only a minor detail is missing, state a provisional assumption and continue.

Once the concept is clear enough, offer an initial product direction before asking for more detail. Surface capabilities the user may not know about, and keep compatible needs together. Ask only a question whose answer could materially redirect the design; do not turn product discovery into a user tutorial or a checklist interview.

## Research

Research when an external fact could change the recommendation: existing products, open-source projects, standards, technical feasibility, costs, or user demand. Search for both supporting and disconfirming evidence. Keep findings linked to sources and dates. If research tools are unavailable, say what could not be verified and propose the highest-value check.

## Compare

Select only meaningful options. Common paths are adopt, adapt, combine, build, or defer; these are prompts, not required categories. Compare each option against the user's outcomes and constraints. Include tradeoffs, costs, risks, dependencies, uncertainty, and what evidence would change the ranking. Explain why a weak option was excluded when that matters.

## Decide

Recommend a path with rationale. Separate a reversible experiment from a consequential commitment. Show the concrete decision and material assumptions before asking for user confirmation. Accept rejection, amendment, pause, or reopening without treating earlier agreement as permanent. Record important decisions using the decision-management reference.

## Deliver

Make the next step actionable. Depending on need, provide a problem definition, research summary, comparison, scoped requirements, acceptance criteria, decision log, or handoff. Check that another person could understand what to do and how to tell whether the design meets its goal. If a durable record is not available, produce a short recovery summary.

## Scale and stop

- **Lightweight:** answer a bounded question directly; state the key reasoning and uncertainty.
- **Moderate:** clarify the problem, compare a few meaningful options, recommend, and capture key criteria.
- **Deep:** investigate consequential or uncertain choices, record evidence and decisions, then prepare a handoff if requested.

Stop when the user has a useful answer or when the remaining uncertainty cannot be resolved with available information. State the unresolved question and the smallest useful next check. Do not prolong discussion to complete a ceremonial sequence.
