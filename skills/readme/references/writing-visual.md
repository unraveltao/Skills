# Writing & Visual Design

## Inputs and scope

Use the confirmed Project Understanding Brief, Reader & Product Brief and (when applicable) approved README Structure Plan. Follow the user-authorized output scope. A structure approval does not itself authorize repository edits; a request for a draft may be satisfied in the response.

## Writing rules

- Use concrete, plain wording suited to the primary reader. Follow the user's language request, otherwise the repository's established README language/style when usable.
- Explain what the project is and what a reader can do with it. Distinguish **features** from **benefits**; avoid generic marketing claims.
- Separate current reality, in-progress work, and future vision. Include only supported claims.
- Preserve useful accurate content. Change only the approved scope; do not turn local improvements into an unrequested rewrite.
- Link to existing deeper docs where they help, after checking paths/anchors. Do not promise nonexistent docs.

## Quick Start and examples

Include a Quick Start only when it serves the reader's first goal. Every prerequisite, install/config/run command, code sample, API, expected output, and dependency/version must be traceable to source/config/docs or supplied by the user with the right label. Prefer the canonical documented interface, then verify it against source/config where practical. Do not derive a command from a filename alone.

Do not call an example tested unless it was actually run and its scope/result recorded. If functional execution is not authorized or safe, retain a clearly evidenced example when useful and report the check as NOT RUN.

## Visuals

Use a visual only for a specific reader benefit. Tables help compare structured alternatives; diagrams help explain relationships; screenshots demonstrate actual UI. Check that image and badge targets exist and the data is current. Never fabricate screenshots, links, badge values, metrics, versions, or license facts. Generated/concept art must be labeled as such and must not impersonate a real product capture. Do not add or edit image resources without authorization.

## Output

Provide a README Draft in the requested format. For a file edit, preserve unrelated sections and inspect the diff after writing. Keep evidence/provenance available for verification, typically in the accompanying report rather than cluttering README prose. Flag unsupported details as questions, cautious wording, or omissions—not invented filler.
